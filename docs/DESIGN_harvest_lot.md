## 1. ขั้นตอนจริงหน้าสวน (ที่ผู้ใช้ยืนยัน)

```
วันที่ 27/07 — 1 วัน = 1 รอบ (ขายทุกวันที่ตัด)
├── ต้น T-001 → ตัดทั้งต้น → ลงตะกร้า → ชั่ง 1 ครั้ง → 45 กก. / 18 ลูก
├── ต้น T-002 → ตัดทั้งต้น → ลงตะกร้า → ชั่ง 1 ครั้ง → 38 กก. / 15 ลูก
├── ต้น T-001 (ตะกร้าที่ 2) → ชั่งอีกครั้ง → 22 กก. / 9 ลูก   ← บวกเข้าต้นเดิม
└── ... (ตัดได้เท่าที่ไหวในวันนั้น สวนร้อยต้นใช้หลายวันจนครบ)
                      ↓
              เทรวมกอง (ของวันนั้น)
                      ↓
        คัดเกรด → A 60 กก. / B 40 กก. / C 20 กก.
                      ↓
              ขายวันเดียวกัน (ราคาต่อเกรด)

วันที่ 28/07 → รอบใหม่ ตัดต้นที่เหลือต่อ แล้วขายวันนั้นอีกรอบ
```

## 2. ทำไมโมเดลปัจจุบันถึงขัดกันเอง

ชีต `การเก็บเกี่ยว` ตอนนี้เก็บ **treeId + เกรด + ราคา ไว้ในแถวเดียวกัน** — แต่ในความจริง
**พอเทรวมกองแล้วคัดเกรด ทุเรียนเกรด A มาจากต้นไหนบ้างไม่มีใครรู้ และไม่มีทางรู้**

ตอนคนสวนชั่งเสร็จ ยังไม่รู้เกรด ยังไม่รู้ราคา — จะกรอกได้ก็ต้องเดา

ผลกระทบกับของที่ใช้อยู่ตอนนี้:

- Dashboard **"สรุปตามเกรด"** ที่คำนวณจากแถวรายต้น → ตัวเลขไม่ตรงความจริง
- **รายได้ต่อต้น** → คำนวณตรงๆ ไม่ได้ ต้องเฉลี่ยตามสัดส่วนน้ำหนัก

## 3. โครงข้อมูลใหม่

### ชีต `การเก็บเกี่ยว` (แก้ของเดิม)

| คอลัมน์ | หมายเหตุ |
|---|---|
| ID | เดิม |
| **รอบที่** | 🆕 `H-25680727` — **สร้างจากวันที่ตัดอัตโนมัติ** (1 รอบ = 1 วัน) |
| ฤดูกาล | เดิม |
| ต้นไม้ | เดิม |
| จำนวนลูก | เดิม (`จำนวน`) |
| **น้ำหนัก (กก.)** | เดิม — ตอนนี้กลายเป็นข้อมูลหลักของแถว |
| เหตุผล | ตัดขาย / ผลเสียหาย |
| รูป, ผู้บันทึก, ผู้บันทึกID, วันที่, วันอนุมัติ, ผู้อนุมัติ | เดิม |
| ~~เกรด~~ | ❌ **ย้ายไปชีตรอบขาย** |
| ~~ราคา~~ | ❌ **ย้ายไปชีตรอบขาย** |

### ชีต `รอบขาย` (สร้างใหม่) — 1 แถวต่อ (รอบ × เกรด)

| คอลัมน์ | ตัวอย่าง |
|---|---|
| รอบที่ | `H-25680727` (= วันที่ตัด) |
| เกรด | A |
| น้ำหนัก (กก.) | 60 |
| ราคา/กก. | 130 |
| รวมเงิน | 7,800 |
| วันที่ขาย | 27/07/2569 |
| ผู้ซื้อ | ล้งเจ๊แดง |
| ผู้บันทึก | ตะวัน |

**รายได้รวมของรอบ** = ผลรวม `รวมเงิน` ทุกแถวของรอบนั้น

### สูตรรายได้ต่อต้น (ประมาณการ)

```
รายได้ของต้น X ในรอบ = (น้ำหนักที่ต้น X ส่งเข้ารอบ ÷ น้ำหนักรวมทุกต้นในรอบ) × รายได้รวมของรอบ
```

> 💡 เป็น**ตัวเลขประมาณ** เพราะเฉลี่ยตามน้ำหนัก ไม่ใช่ตามเกรดจริง (ซึ่งตามกลับไม่ได้)
> แต่เพียงพอสำหรับเทียบว่า "ต้นไหนทำเงินได้ดีกว่ากัน" ตามที่ผู้ใช้ต้องการ
> น้ำหนักที่ชั่งจากสวนอาจมากกว่าน้ำหนักที่ขายได้ (มีของคัดทิ้ง) — สัดส่วนยังถูกอยู่

## 4. Flow ใหม่

### คนสวน (เหลือ 3 ขั้น จากเดิม 7)

```
สแกน QR → พิมพ์ "น้ำหนัก จำนวนลูก" (เช่น "45 18") → ถ่ายรูปตาชั่ง → ยืนยัน
```

- **สแกนต้นเดิมซ้ำได้** → บวกน้ำหนัก/จำนวนเข้ารอบที่เปิดอยู่ (ตะกร้าที่ 2, 3, ...)
- ไม่ต้องกรอกเกรด ไม่ต้องกรอกราคา — ตอนนั้นยังไม่รู้

### เจ้าของ/admin — ปิดรอบ + บันทึกการขาย (วันละครั้ง)

```
เมนู "ปิดรอบขาย" → ระบบสรุปให้ว่ารอบนี้มีกี่ต้น รวมกี่ กก.
   → กรอกทีละเกรด: เกรด A: น้ำหนัก / ราคา
   → ยืนยัน → ระบบเฉลี่ยรายได้กลับไปทุกต้นในรอบอัตโนมัติ
```

## 5. เรื่อง "รอบ" — **1 รอบ = 1 วัน** (สรุปสุดท้าย)

> ผู้ใช้เปลี่ยนกฎหน้างานเป็น **"ขายทุกวันที่ตัด"** — ตัดวันไหนขายวันนั้น ไม่กองข้ามวันอีกแล้ว

นี่ทำให้ design ง่ายลงมาก:

| เดิม (รอบ 1-3 วัน) | ใหม่ (รอบ = 1 วัน) |
|---|---|
| ต้องมีปุ่ม "เปิดรอบ" | ❌ ไม่ต้อง — รอบเกิดเองจากวันที่ |
| ต้องเก็บสถานะ "รอบไหนเปิดอยู่" | ❌ ไม่ต้อง — วันที่คือรอบ |
| ต้องเตือนเมื่อรอบค้างเกิน 3 วัน | ✅ เหลือแค่เตือน "วันนี้ยังไม่บันทึกการขาย" |
| ต้องกัน race ตอนหลายคนเปิดรอบพร้อมกัน | ❌ ไม่มีปัญหานี้แล้ว |

**รหัสรอบ = วันที่ตัด** เช่น `H-25680727` — สร้างจากวันที่อัตโนมัติ ไม่มีใครต้องกดอะไร

- **คนสวน:** สแกน → บันทึกน้ำหนัก/จำนวนลูก → เข้ารอบของวันนั้นเองอัตโนมัติ
- **เจ้าของ:** ตอนเย็นกด "บันทึกการขายวันนี้" → กรอกเกรด/น้ำหนัก/ราคา → ระบบเฉลี่ยรายได้กลับไปทุกต้นที่ตัดวันนั้น
- **รายการ "ผลเสียหาย"** อยู่ในรอบด้วย แต่ **ไม่นับในน้ำหนักที่ใช้เฉลี่ยรายได้** (ไม่ได้ขาย)

### 🚨 Safeguard ที่เหลือ: เตือนวันที่ยังไม่บันทึกการขาย

ถ้ามีการตัดในวันหนึ่งแต่ไม่มีแถวในชีต `รอบขาย` ของวันนั้น = ยังไม่ได้บันทึกการขาย

ใช้ `PushScheduler.gs` ที่มีอยู่แล้ว (รันวันละ 6 ครั้ง) push เตือนเจ้าของตอนเย็น — ง่ายกว่าเดิมมากเพราะเช็คแค่ "วันไหนมีตัดแต่ไม่มีขาย"

### ⚠️ จุดเดียวที่ยังต้องเผื่อ: บันทึกย้อนหลัง

ถ้าคนสวนลืมบันทึกตอนอยู่หน้าสวน (เน็ตไม่มี / แบตหมด) แล้วมาบันทึกวันรุ่งขึ้น → รายการจะตกไปอยู่รอบของ**วันที่บันทึก** ไม่ใช่**วันที่ตัดจริง**

**ทางแก้ที่แนะนำ (เรียบง่าย):** ตอนบันทึกการขาย ให้เจ้าของเลือกวันที่ได้ (default = วันนี้) และในหน้าสรุปรอบแสดงรายการทั้งหมดให้ตรวจก่อนยืนยัน — ถ้าเห็นของแปลกปนมาก็ย้ายได้

### ผลต่อความแม่นของ "รายได้ต่อต้น"

**แม่นขึ้นกว่าเดิมมาก** เพราะทุเรียนในรอบเดียวกันตัดวันเดียวกัน สุกใกล้เคียงกัน เกรดจึงกระจายตัวใกล้เคียงกันด้วย

ยังเป็นค่าประมาณอยู่ (เฉลี่ยตามน้ำหนัก ไม่ใช่เกรดจริงรายต้น) — **หน้ารายงานยังต้องเขียนกำกับว่าเป็นค่าประมาณ** แต่ความคลาดเคลื่อนน้อยกว่าแบบรอบ 3 วันชัดเจน

## 6. ผลกระทบ / ขอบเขตงาน

การเปลี่ยนนี้ **ไม่ใช่งานเล็ก** — กระทบทั้งสายข้อมูล:

| ส่วน | ผลกระทบ |
|---|---|
| ชีต `การเก็บเกี่ยว` | ลบ 2 คอลัมน์ เพิ่ม 1 คอลัมน์ — **ข้อมูลเดิมที่มีเกรด/ราคาต่อต้นต้องมีแผนรองรับ** |
| `approveItem()` | flow อนุมัติเปลี่ยน — ไม่มีเกรด/ราคาให้บันทึกแล้ว |
| Dashboard "สรุปตามเกรด" | ต้องอ่านจากชีตรอบขายแทน |
| Dashboard รายได้ | ต้องอ่านจากชีตรอบขาย |
| `getDashboardTotal/ByGrade` | เขียนใหม่ |
| Flex message สรุปรายการ | เปลี่ยนฟิลด์ที่แสดง |
| `getTreeHistoryPublic()` (หน้า TreeInfo) | ประวัติเปลี่ยนรูปแบบ |
| QR print (`getTreesPrintInfoBulkWeb`) | ใช้ `คงเหลือ` เหมือนเดิม — ไม่กระทบ |
| Automated test 117 เคส | ส่วนที่แตะ harvest ต้องเขียนใหม่ |

### ทางเลือกเรื่องข้อมูลเก่า

1. **เก็บชีตเดิมไว้เป็น archive** แล้วเริ่มชีตใหม่ตอนขึ้นฤดูกาลใหม่ (ปลอดภัยสุด แนะนำ)
2. Migrate ข้อมูลเก่า → สร้างรอบย้อนหลัง 1 รอบต่อ 1 แถวเดิม (ได้ข้อมูลต่อเนื่อง แต่ตัวเลขเกรดเดิมก็ไม่ตรงความจริงอยู่ดี)

## 7. สิ่งที่ตัดสินใจแล้ว (จากผู้ใช้)

- ✅ ตอนชั่งต่อต้น **นับจำนวนลูกด้วย** — จะได้หัก "คงเหลือบนต้น" ได้ตรง และคำนวณน้ำหนักเฉลี่ยต่อลูกได้
- ✅ **สแกนต้นเดิมซ้ำได้ ระบบบวกให้** — คนสวนไม่ต้องคิดเลขเอง
- ✅ **อยากรู้รายได้ต่อต้น ยอมให้เป็นตัวเลขเฉลี่ยตามน้ำหนัก**
- ✅ **1 รอบ = 1 วัน** (เปลี่ยนกฎหน้างานเป็น "ขายทุกวันที่ตัด") — ไม่ต้องมีปุ่มเปิด/ปิดรอบ รหัสรอบสร้างจากวันที่อัตโนมัติ

## 8. ยังไม่ได้ตัดสินใจ (เหลือเรื่องเดียว)
